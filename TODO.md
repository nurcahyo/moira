## From plan 02b (idempotency replay)

Surfaced by four adversarial QA lenses (correctness, security, test-integrity, conventions). Items
fixed inside 02b are not listed here; these are the ones deliberately left for a later plan.

- [x] Unify `runtime_admin.rs`'s divergent `actor_fingerprint` with `admin.rs`'s — source: plans/02b-idempotency-replay.md — **Done by plan 06** (commit `27fe021`). The runtime copy fingerprinted only `(actor_type, subject, api_key_id)`, omitting seven identity fields, while writing into the **same** `idempotency_records` table as the 10-field admin version; three actors differing only by issuer / application / tenant all hashed to `oBmwFVvCAAAh`, so two `TrustedJwt` actors sharing a `sub` across different registered issuers could replay each other's runtime-policy responses. There is now exactly one definition, `src/application/admin/shared.rs:344`, and `src/application/runtime_admin.rs:14` imports it. A read-only `legacy_actor_fingerprint` fallback survives so pre-deploy ledger rows stay replayable — its removal is the separate item below.
- [ ] Remove the legacy `actor_fingerprint` fallbacks after the plan-06 deploy — source: plans/02b-idempotency-replay.md (via plan 06) — **needs an owner and a date; this is the scheduling issue #96 asked for.** Four `TODO(post-deploy)` markers: `src/application/runtime_admin.rs:938` and `:1039`, `src/application/public.rs:1060` and `:2239`. **Trigger:** the date plan 06 reaches production, plus 24 hours — `idempotency_records.expires_at` is set 24h ahead, so that is when the last ledger row written under the old fingerprint expires. Gated on a **deploy**, not a merge, which is why no plan owns it. Removing it early means a client retrying an idempotent request across the deploy boundary misses its ledger row and **executes the side effect a second time**; removing it late costs only dead code. If in doubt, wait longer. See [`docs/decisions-taken.md`](./docs/decisions-taken.md) §5.
- [ ] Prune the idempotency ledger — source: plans/02b-idempotency-replay.md — plan 04's retention worker is the designated pruner. `WorkerRegistry`'s `"retention-cleanup"` spec currently has no execution body, and the opportunistic purge in `claim_idempotency` only deletes rows for the *same* `(key_hash, fingerprint, operation)`, so rows under distinct keys are never reclaimed. Worse than incidental growth: deterministic-failure caching (`src/application/admin_command.rs:210-235`) commits a ledger row for a *rolled-back* cacheable 4xx, so an actor holding only `moira:rag-documents:ingest` can mint one row per request by ingesting non-existent document ids under fresh keys — cheaper than a real mutation and directly attacker-controllable. **If plan 04 slips, 02b ships unbounded growth.**
- [ ] Bound the advisory-lock poll against the connection pool — source: plans/02b-idempotency-replay.md — `claim_idempotency` (`src/infra/repositories/admin.rs:563-581`) polls `pg_try_advisory_xact_lock` every 20ms for up to 5s *inside an already-open transaction on a pooled connection*, and `config/default.toml:10` sets `max_connections = 10`. Ten concurrent duplicate-key requests pin the whole pool for five seconds; the eleventh request on *any* route, including `/v1/responses`, blocks on pool acquire. `ingest` additionally now holds its `for update` document-row lock for the full claim→finalize window. Pre-existing primitive, but 02b lowers the bar for reaching it.
- [ ] Bound `Idempotency-Key` length and charset — source: plans/02b-idempotency-replay.md — `src/application/context.rs:30` takes the header verbatim, unlike `runtime_admin.rs:722`'s `validate_key` (1–128 chars). Nothing overflows since the key is hashed to a fixed-width column, so this is hygiene rather than a hole.
- [ ] Cover the advisory-lock **timeout** arm of `idempotency_in_progress` for the RAG routes — source: plans/02b-idempotency-replay.md — `in_progress_claim_returns_a_catalogued_idempotency_in_progress_error` forces the *unfinalized-record* arm with direct SQL, and the concurrency test's loser always waits and replays rather than timing out, so the 5s-deadline arm (`src/infra/repositories/admin.rs:574-579`) is exercised only by `advisory_lock_timeout_is_transient_and_does_not_mutate_or_cache` on the admin path. The code path is shared, so this is a coverage gap rather than a hole.

- [ ] Decide whether a replayed request should leave an audit trace — source: plans/02b-idempotency-replay.md — the replay branch (`src/application/admin_command.rs:175-178`) returns before the mutation closure, so no `audit_logs` row is written. ## From plan 03 (security hardening)

Surfaced by four adversarial QA lenses (SSRF/JWKS, hashing migration, middleware/availability,
test integrity). Items fixed inside 03 are not listed here; these are deliberately deferred.

- [ ] Pepper `actor_fingerprint` too — source: plans/03-security-hardening.md — it is the one column in `idempotency_records` still produced by the unkeyed `secret_fingerprint`, in all three producers (`src/application/admin.rs`, `src/application/public.rs`, `src/application/runtime_admin.rs`). P1-1's own threat model applies *harder* here than to request bodies: a JWT `sub` / `external_user_id` / email is far lower-entropy than a JSON body, and once an attacker knows the actor type the tuple is enumerable. Plan 03 scoped only `idempotency_key_hash`/`request_hash`/`content_hash`, so this is out of scope by the letter — but the table is not actually hardened until it is done, and **plan 07 is what fills this column with human identity**. Doing it after 07 needs the same dual-read/dual-lookup dance, since `actor_fingerprint` is part of the unique index. Cheapest while the scaffolding is fresh.
- [ ] Bound stale-JWKS retention in time — source: plans/03-security-hardening.md — `src/security/auth.rs` serves a retained cache entry on *any* fetch failure with no maximum staleness, and neither `entries` nor `locks` is ever evicted. A key revoked at the IdP stays trusted for as long as the endpoint keeps failing — indefinitely. The right availability call short-term, but it converts "DoS the IdP's JWKS endpoint" into "a compromised signing key can never be rotated out". Wants a `max_stale_seconds` ceiling plus entry eviction; both maps are also keyed by admin-controlled URL strings.
- [ ] Retire the legacy-hash acceptance window — source: plans/03-security-hardening.md — plan 03 adds `idempotency.accept_legacy_hashes` (default `true`). Flip it to `false` after one full 24h retention period has elapsed post-deploy, which also drops the unconditional extra `SELECT` on every idempotent `/v1/responses` request.
- [ ] Redact `Debug` on pepper-bearing types — source: plans/03-security-hardening.md — `IdempotencyHasher` derives `Debug` over `pepper: Vec<u8>`, `AdminCommandRunner` derives `Debug` while holding it, and `IdempotencySettings` derives `Debug` over `pepper_base64`. **No active leak today** — a reviewer grepped every `{:?}`/`?state`/`?settings` path reaching them and found none — but `src/application/conversation.rs` already uses `format!("{spec:?}")` in the same area, so the idiom is live. Custom `Debug` impls would make the invariant structural rather than incidental. `ApiKeyHasher` has the identical exposure; plan 03 copied a pre-existing pattern rather than introducing a regression.
- [ ] Sweep expired rows on the public idempotency ledger — source: plans/03-security-hardening.md — the admin transaction sweeps both key hashes before lookup; the public path has none. `claim_idempotency` does `on conflict do nothing` then reads with `expires_at > now()`, so when the conflicting row is expired the read returns `None` and the caller gets a **permanent** `409 execution_in_progress` for that key. Pre-existing; plan 03 rewrote the function and left it. Plan 04's retention worker is the natural owner.
- [ ] Document that `CatchPanicLayer` does not cover streaming-body panics — source: plans/03-security-hardening.md — tower-http wraps only `inner.call(req)` and the response future, not the response body. Measured: `/internal/test/panic` returns a clean 500 envelope, but a panic *after* the first SSE frame returns zero bytes and a bare connection close. Latent today (Moira's SSE handler contains no `unwrap`/`expect`/`panic!`), but any future one truncates a stream indistinguishably from a network cut, with no terminal event and no 500.
- [ ] Re-run plan 03's gates against PostgreSQL 16 in CI — source: plans/03-security-hardening.md — all four lenses independently assessed the PG18.3 deviation as not weakening any of their findings (every finding is application-layer: Rust control flow, HTTP status codes, in-process cache locking). The one test where a lock-manager difference could plausibly matter is `concurrent_same_key_claims_still_produce_one_ledger_row`.

- [ ] Close the lost-update window on the other ~28 versioned admin mutations — source: plans/04-durability-correctness.md — plan 04 closed the TOCTOU on `PUT .../execution-policy` with a SQL-level version check, because that endpoint is the one it owns. - [ ] Add page-through coverage for the remaining list endpoints — source: plans/04-durability-correctness.md — e2e walk tests exist for applications, audit-events, routes and conversations/messages. `providers`, `provider_models`, `credentials`, `user_credentials`, `system_keys`, `consumer_keys`, `trusted_jwt_issuers`, `memories`, `rag_collections` and `rag_documents` have none. - [ ] Re-verify the pagination index choices on PostgreSQL 16 — source: plans/04-durability-correctness.md — the `EXPLAIN` numbers written into `src/infra/repositories/conversation.rs` justifying the new indexes were measured on 18.3 and are cited as such.
