## From plan 02b (idempotency replay)

Surfaced by four adversarial QA lenses (correctness, security, test-integrity, conventions). Items
fixed inside 02b are not listed here; these are the ones deliberately left for a later plan.

- [ ] Unify `runtime_admin.rs`'s divergent `actor_fingerprint` with `admin.rs`'s — source: plans/02b-idempotency-replay.md — `src/application/runtime_admin.rs:702` fingerprints only `(actor_type, subject, api_key_id)`, omitting `trusted_jwt_issuer_id`, `internal_application_id`, `application_id`, `tenant_id`, `external_user_id`, `external_tenant_id` and `delegated_subject`, while writing into the **same** `idempotency_records` table as the 10-field `admin.rs:1375` version. Proven empirically: three actors differing only by issuer / application / tenant all hash to `oBmwFVvCAAAh` under the runtime copy. Two `TrustedJwt` actors sharing a `sub` across different registered issuers can therefore replay each other's `POST /api/v1/admin/routes`, `routing-policies`, `agent-profiles` or `provider-runtime-policy` responses. **Pre-existing on `main`; 02b explicitly excludes `runtime_admin.rs` and plan 06 owns the unification.** 02b's routes are unaffected because `operation` is part of the unique index and the `rag.*` operations are disjoint.
- [ ] Prune the idempotency ledger — source: plans/02b-idempotency-replay.md — plan 04's retention worker is the designated pruner. `WorkerRegistry`'s `"retention-cleanup"` spec currently has no execution body, and the opportunistic purge in `claim_idempotency` only deletes rows for the *same* `(key_hash, fingerprint, operation)`, so rows under distinct keys are never reclaimed. Worse than incidental growth: deterministic-failure caching (`src/application/admin_command.rs:210-235`) commits a ledger row for a *rolled-back* cacheable 4xx, so an actor holding only `moira:rag-documents:ingest` can mint one row per request by ingesting non-existent document ids under fresh keys — cheaper than a real mutation and directly attacker-controllable. **If plan 04 slips, 02b ships unbounded growth.**
- [ ] Bound the advisory-lock poll against the connection pool — source: plans/02b-idempotency-replay.md — `claim_idempotency` (`src/infra/repositories/admin.rs:563-581`) polls `pg_try_advisory_xact_lock` every 20ms for up to 5s *inside an already-open transaction on a pooled connection*, and `config/default.toml:10` sets `max_connections = 10`. Ten concurrent duplicate-key requests pin the whole pool for five seconds; the eleventh request on *any* route, including `/v1/responses`, blocks on pool acquire. `ingest` additionally now holds its `for update` document-row lock for the full claim→finalize window. Pre-existing primitive, but 02b lowers the bar for reaching it.
- [ ] Bound `Idempotency-Key` length and charset — source: plans/02b-idempotency-replay.md — `src/application/context.rs:30` takes the header verbatim, unlike `runtime_admin.rs:722`'s `validate_key` (1–128 chars). Nothing overflows since the key is hashed to a fixed-width column, so this is hygiene rather than a hole.
- [ ] Cover the advisory-lock **timeout** arm of `idempotency_in_progress` for the RAG routes — source: plans/02b-idempotency-replay.md — `in_progress_claim_returns_a_catalogued_idempotency_in_progress_error` forces the *unfinalized-record* arm with direct SQL, and the concurrency test's loser always waits and replays rather than timing out, so the 5s-deadline arm (`src/infra/repositories/admin.rs:574-579`) is exercised only by `advisory_lock_timeout_is_transient_and_does_not_mutate_or_cache` on the admin path. The code path is shared, so this is a coverage gap rather than a hole.
- [ ] Assert the `docs/i18n-response-catalog.json` mirror automatically — source: plans/02b-idempotency-replay.md — the two catalog tests assert the **Rust** side only; the JSON mirror was verified by hand (64 entries, 62 unique, the two pre-existing duplicates `idempotency_conflict` and `rate_limited` left alone per instruction). CONVENTIONS §4 rule 4 defers the drift test to plan 06, so this is compliant, not a violation.
- [ ] Decide whether a replayed request should leave an audit trace — source: plans/02b-idempotency-replay.md — the replay branch (`src/application/admin_command.rs:175-178`) returns before the mutation closure, so no `audit_logs` row is written. Before 02b every RAG write produced one; now a repeated keyed request leaves no record that a second request was received. Defensible, and pinned by the concurrency test, but it is an observable behavioural change.
- [ ] Make `AdminCommandOutcome.status` load-bearing — source: plans/02b-idempotency-replay.md — all three service methods return `Ok(outcome.response)` and discard `outcome.status`, `outcome.resource_id` and `outcome.replayed`; the handlers re-derive the status as a hardcoded literal. Stored and hardcoded values coincide today, so replay is verbatim by coincidence rather than by construction. The moment any of these operations gains a conditional status (e.g. ingest returning `202` once plan 11 lands) replay will silently return the wrong one. `src/application/public.rs:179` already honours `outcome.status` on its own path. Same pattern exists in `admin.rs`, so pre-existing.
