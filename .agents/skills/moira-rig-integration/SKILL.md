# Moira Rig Integration

## Core Rule

Moira orchestrates runtime config, identity claims, credentials, routing, and streaming; Rig owns AI execution primitives.

`rig_core` is imported by exactly two files today:

| File | Role |
|---|---|
| `src/orchestration/runtime_factory.rs` | the execution seam — clients, models, requests, responses, errors, usage, stream chunks, and `DomainMessage` → `Message` conversion |
| `src/application/execution.rs` | request assembly (`CompletionRequest`) and output reading |

Adding a third is a design change, not an implementation detail. Justify it before you write it. `grep -rl rig_core src` must keep returning exactly those two paths.

Plan 06 deleted the legacy V1 path entirely: `src/orchestration/executor.rs` (a raw-`reqwest` client that used Rig only to compute a base URL) and its uncompiled consumer `src/http/chat.rs`, along with the `ChatCompletionRequest` / `ChatMessage` DTOs, no longer exist. Do not recreate them under any name. "Derive a URL from Rig, then hand-roll the request" is the canonical anti-pattern; new work goes through `RuntimeFactory`.

`src/domain/runtime.rs` and `src/application/public.rs` used to import `Message`; plan 06 (P2-2) replaced that with `crate::domain::DomainMessage` so `src/domain` carries no upstream dependency. `src/domain/message.rs` is Moira's caller-input message shape, **not** a re-expression of Rig's `Message` — it models only role plus text/image content parts, and everything else about a Rig message stays behind `runtime_factory.rs`.

Never wrap Rig in a second generic LLM client abstraction. The only abstraction permitted over Rig is `RuntimeFactory` — a factory that returns Rig's own model types.

## Version Pin

- `Cargo.toml` declares `rig-core = "0.40"`; `Cargo.lock` pins **0.40.0**.
- Vendored authority: `/Users/nalhide/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/rig-core-0.40.0`.
- The crate is `rig_core` in Moira source. The crate internally does `extern crate self as rig;` (`src/lib.rs:143`), so upstream docs and examples say `rig::…`. Translate to `rig_core::…`; never write `rig::` in Moira.

**Verification rule: read the vendored source before you write the call.** In 0.40 most provider model types are `pub type` aliases over generics, several error and content types are `#[non_exhaustive]`, and some methods are macro-generated rather than written out. Web docs and GitHub examples track `main`, not 0.40.0. When they disagree with the vendored source, the vendored source wins. If you cannot find a signature in the vendored tree, the API does not exist — do not write it.

```bash
RIG=/Users/nalhide/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/rig-core-0.40.0
rg -n 'pub trait CompletionModel' -A 40 "$RIG/src/completion/request.rs"   # 613
rg -n 'pub struct CompletionRequest' -A 32 "$RIG/src/completion/request.rs" # 668
rg -n 'pub fn completions_api' "$RIG/src/providers/openai/client.rs"        # 191
rg -n 'pub type CompletionModel' "$RIG/src/providers"                       # aliases
```

**Grep for the definition, not just the name.** Two traps in this crate:

- Provider model types are aliases, so `pub struct CompletionModel` finds nothing for openai/anthropic/deepseek/azure. Only `gemini::completion::CompletionModel` is a real struct (`src/providers/gemini/completion.rs:59`).
- `CompletionError::provider_response_status()` has no literal `fn` definition on `CompletionError`. It is generated by `crate::provider_response::impl_provider_response_helpers!(CompletionError)` (`src/completion/request.rs:125`) from the macro body at `src/provider_response.rs:65-163`. Grepping `fn provider_response_status` in `request.rs` returns only the *forwarding* copies on `PromptError` (`:224`) and `StructuredOutputError` (`:286`) — different types that delegate inward. Read the macro before changing error classification.

  The macro also gives `CompletionError` `provider_response_body()` and `provider_response_json()`. Its doc warns that `provider_response_status()` **can return a 2xx** — some providers send an error envelope with a success status. Never infer failure from the status; the error's existence already means the call failed.

## Ownership Boundary

| Concern | Owner | Where |
|---|---|---|
| Provider HTTP transport, wire encoding, SSE frame parsing | Rig | vendored crate |
| Per-provider `CompletionModel` types, `CompletionError` taxonomy, token-usage extraction | Rig | vendored crate |
| Provider client construction from resolved config + credential | Moira | `orchestration/runtime_factory.rs` |
| Base-URL normalisation | Moira | `orchestration/provider_url.rs` (`normalize_openai_base_url`) |
| Credential *resolution* and precedence | Moira | `infra/repositories/runtime.rs` (`resolve_runtime_credential`) — **not** orchestration |
| Credential-*type* gating | Moira | `application/execution.rs` (`supported_credential_types`) mirrored by `orchestration/runtime_factory.rs` (`require_credential_type`) |
| Handle caching, TTL, invalidation | Moira | `orchestration/controls.rs` (`ProviderRuntimeCache`); runtime-config caching is `orchestration/runtime_cache.rs` (`RuntimeConfigCache`) |
| Routing, fallback, retry/backoff, deadlines, circuit breaking, permits | Moira | `orchestration/controls.rs`, `application/execution.rs` |
| Public DTO → `DomainMessage` | Moira | `application/public.rs` |
| `DomainMessage` → `rig_core::completion::Message` | Moira | `orchestration/runtime_factory.rs` (`impl TryFrom<&DomainMessage> for Message`, `rig_chat_history`) |
| Runtime event envelopes, public SSE contract, persistence, audit | Moira | `application/*`, `http/public.rs` |
| Failure classification and sanitised error text | Moira | `classify_completion_error` in `runtime_factory.rs` |

Rig model handles never escape `orchestration`. `RuntimeModelHandle` is re-exported from `src/orchestration/mod.rs`, cached inside `orchestration/controls.rs`, and its only consumer outside `orchestration` is `application/execution.rs` (as `Arc<RuntimeModelHandle>`). Nothing in `http`, `infra`, or `domain` may hold one.

## Where Rig May Appear

Allowed imports of `rig_core`:

- `src/orchestration/runtime_factory.rs` — the full execution surface (clients, models, `CompletionRequest`, `CompletionResponse`, `CompletionError`, `Usage`, `StreamedAssistantContent`).
- `src/application/execution.rs` — `CompletionRequest` and `rig_core::schemars::Schema` for request assembly.

Forbidden:

- `src/domain/**`, `src/application/**` other than `execution.rs` (including `application/public.rs` and every module under `application/admin/`), `src/http/**`, `src/infra/**`, `src/security/**`, `src/config/**`, `src/i18n/**`, `src/app/**` — no `rig_core` import. They speak `DomainMessage` and Moira envelopes only.
- Any new "V2 executor", "chat client", or provider HTTP module. The deleted `src/orchestration/executor.rs` / `src/http/chat.rs` pair is the shape to recognise and refuse: a Rig client constructed only to read `base_url()`, followed by hand-rolled `reqwest` calls against `/chat/completions` with a plaintext key. New work goes through `RuntimeFactory`.

## The RuntimeFactory / RuntimeModelHandle Seam

One async trait, one enum, one construction site.

```rust
#[async_trait]
pub trait RuntimeFactory: Send + Sync {
    async fn build_completion_model(
        &self,
        provider: &ResolvedProviderConfiguration,
        model_key: &str,
        credential: &ResolvedCredential,
        policy: &ProviderRuntimePolicyRecord,
    ) -> Result<RuntimeModelHandle, AppError>;
}

#[derive(Clone)]
pub enum RuntimeModelHandle {
    OpenAi(openai::completion::CompletionModel),
    Anthropic(anthropic::completion::CompletionModel),
    Gemini(gemini::completion::CompletionModel),
    DeepSeek(deepseek::CompletionModel),
    AzureOpenAi(azure::CompletionModel),
}
```

**Why an enum and not `Box<dyn CompletionModel>`.** `rig_core::completion::CompletionModel` (`src/completion/request.rs:613`) has associated types (`Response`, `StreamingResponse`, `Client`), an `impl Into<String>` argument on `make`, and RPITIT `completion`/`stream` methods returning `impl Future`. It is not object-safe. Enum dispatch delegating to a generic free function is the only viable shape; do not attempt to erase it.

```rust
impl RuntimeModelHandle {
    pub async fn completion(
        &self,
        request: CompletionRequest,
    ) -> Result<RuntimeCompletionOutput, ExecutionFailure> {
        match self {
            Self::OpenAi(model) => completion_with_model(model, request).await,
            Self::Anthropic(model) => completion_with_model(model, request).await,
            Self::Gemini(model) => completion_with_model(model, request).await,
            Self::DeepSeek(model) => completion_with_model(model, request).await,
            Self::AzureOpenAi(model) => completion_with_model(model, request).await,
        }
    }
}

async fn completion_with_model<M>(
    model: &M,
    request: CompletionRequest,
) -> Result<RuntimeCompletionOutput, ExecutionFailure>
where
    M: RigCompletionModel,
{
    let response = model
        .completion(request)
        .await
        .map_err(classify_completion_error)?;
    Ok(output_from_response(response))
}
```

The streaming helper restates the associated-type bounds:

```rust
where
    M: RigCompletionModel,
    M::StreamingResponse:
        Clone + Unpin + rig_core::completion::GetTokenUsage + Serialize + Send + 'static,
```

`Clone + Unpin + GetTokenUsage` are what `StreamingCompletionResponse<R>` itself demands (`src/streaming.rs:243-246`); `Serialize` is already on the trait's associated type; `Send + 'static` are Moira's, needed to erase the stream into `RuntimeItemStream = Pin<Box<dyn Stream<..> + Send>>`. Restating them is required because Rust does not infer associated-type bounds through a generic free function.

Import alias is mandatory: `use rig_core::completion::CompletionModel as RigCompletionModel;` — Moira has its own model concepts and the bare name collides.

Construction always goes `builder → build() → completion_model(model_key)`. `CompletionClient` (`src/client/completion.rs:9`) is imported solely so its provided method `completion_model(&self, model: impl Into<String>) -> Self::CompletionModel` (`:28`) is in scope; it just forwards to `CompletionModel::make`. For OpenAI you must call `.completions_api()` after `.build()`: `openai::Client<H>` is an alias for `client::Client<OpenAIResponsesExt, H>` (`src/providers/openai/client.rs:49`) — the **Responses API** client. `completions_api(self) -> CompletionsClient<H>` (`:191`) swaps the extension to `OpenAICompletionsExt` (`:54`), which is what yields `openai::completion::CompletionModel` (`src/providers/openai/completion/mod.rs:1533`).

Details of each provider arm belong to `.agents/skills/moira-rig-providers/SKILL.md`.

## Rules Against a Parallel LLM Abstraction

1. Do not introduce a `trait LlmClient` / `trait ChatModel` / `trait Provider` that mirrors `CompletionModel`. If you need behaviour across providers, add a method to `RuntimeModelHandle` that matches and delegates to a generic free function.
2. Do not define Moira structs that duplicate `CompletionRequest`, `CompletionResponse`, `AssistantContent`, or `Usage`. Moira's `RuntimeStreamItem` / `RuntimeCompletionOutput` / `UsageSummary` exist to *narrow* Rig output into the persisted and public contract, not to re-express it. `DomainMessage` is the one deliberate counterpart on the input side, and it is a strict subset — role plus text/image parts. Do not grow it toward parity with `Message`: tool calls, tool results, reasoning, audio, video, and documents belong behind `runtime_factory.rs`, and adding any of them here means designing the feature, not widening a DTO.
3. Do not add a provider by hand-rolling HTTP. If Rig 0.40 lacks a provider, the answer is `AppError::Config` (as `ProviderType::Custom` does today), or an upstream contribution — not a bespoke client.
4. Do not re-export Rig types from `src/domain` or `src/http`. There is no exception; since plan 06 (P2-2), `src/domain` has no `rig_core` import at all.
5. Keep exactly one conversion point per direction: public DTO → `DomainMessage` in `application/public.rs`; `DomainMessage` → `Message` in `runtime_factory.rs`; `CompletionError` → `ExecutionFailure` in `classify_completion_error`; `Usage` → `UsageSummary` in `usage_from_rig`. Adding a second conversion site is a review-blocking defect.

## Workflow

1. Read `skills/moira-project-structure/SKILL.md`, then this file, then the sibling skill(s) from the Skill Map that own the change.
2. Locate the current behaviour in the two allowed files (`orchestration/runtime_factory.rs`, `application/execution.rs`). If the change seems to need a third, stop and justify it.
3. Open the vendored crate and verify every type path, field name, and method signature you intend to use. Prefer `rg -n` over memory. Record the `path:line` you verified against in the PR description or commit body.
4. Implement inside the existing seam. Provider work → the `match provider.provider_type` arm. Request work → `build_completion_request`. Stream work → `start_stream_with_model`. Error work → `classify_completion_error`.
5. Preserve redaction invariants: hand-written `Debug` on anything holding a handle or a secret (`RuntimeModelHandle`, `ResolvedCredential`), `expose_secret()` called at most once and only at the provider builder, provider error bodies never propagated (`safe_config_error`, `safe_provider_error_message`). Never log, serialise, or embed plaintext keys, decrypted material, or internal prompts.
6. If the change alters a public status code, error code, event type, or SSE payload, follow `.agents/skills/moira-openapi/SKILL.md` as well — the sanitised failure message is part of the public contract and part of the idempotency replay record.
7. Extend tests at the boundary the repo already uses: the scripted OpenAI-compatible Axum server in `tests/support/mock_openai.rs`, plus unit tests inside `runtime_factory.rs`. Do not mock Rig types. See `.agents/skills/moira-rig-errors-testing/SKILL.md`.
8. Update `docs/rig-integration.md` when the seam itself changes.

## Upgrading rig-core

Do this deliberately; the pin is load-bearing.

1. Bump `Cargo.toml`, run `cargo update -p rig-core`, and record the new exact version from `Cargo.lock`.
2. Re-vendor-read. Diff the new crate's `src/completion/request.rs`, `src/completion/message.rs`, `src/streaming.rs`, `src/client/mod.rs`, `src/client/completion.rs`, and each provider module Moira names.
3. Check the four known break surfaces:
   - `CompletionRequest` (`src/completion/request.rs:668`) is struct-literal-constructed in `build_completion_request` with all 10 fields — `model`, `preamble`, `chat_history`, `documents`, `tools`, `temperature`, `max_tokens`, `tool_choice`, `additional_params`, `output_schema` — and has **no** `Default` impl. Any added upstream field breaks that call site by design, which is the point. Fill it explicitly; never reach for `..Default::default()`.
   - `CompletionError` is `#[non_exhaustive]` (`src/completion/request.rs:88`); `classify_completion_error` must keep classifying via `provider_response_status()` rather than variant names. It currently matches on the `Option<u16>` status, so it is already variant-agnostic — keep it that way.
   - `AssistantContent` (`src/completion/message.rs:60`) and `StreamedAssistantContent` (`src/streaming.rs:1042`) are *not* `#[non_exhaustive]`, so new upstream variants become hard compile errors in `start_stream_with_model` — good. But `text_from_choice` matches `AssistantContent` with a `_ => None` catch-all, so a new variant there is silently dropped with no compiler warning. Audit that arm explicitly on every bump.
   - Provider type aliases move. Four of the five `RuntimeModelHandle` variants hold aliases, not structs: `openai::completion::CompletionModel` (`openai/completion/mod.rs:1533`), `anthropic::completion::CompletionModel` (`anthropic/completion.rs:1545`), `deepseek::CompletionModel = openai::completion::GenericCompletionModel<DeepSeekExt, H>` (`deepseek.rs:159`), `azure::CompletionModel = openai::completion::GenericCompletionModel<AzureExt, H>` (`azure.rs:555`). Only `gemini::completion::CompletionModel` is a struct (`gemini/completion.rs:59`). A re-home or a generic-parameter change silently retypes the enum.
4. Re-verify the credential and URL contract end to end with `tests/execution_lifecycle.rs` — it asserts the exact `Authorization` header, request body shape, and SSE framing against a real HTTP server, which is the only thing that proves Rig's encoder still matches expectations.
5. Update every skill in the family that cites a `path:line`, and update the version stated at the top of this file.
6. Run the full validation set below plus a manual smoke against one live provider before merge.

## Pitfalls

- `openai::Client` defaults to the Responses API. Forgetting `.completions_api()` yields a different model type and a different wire format.
- `CompletionResponse::message_id` is `None` for OpenAI Chat Completions, Anthropic, Gemini, DeepSeek, and Azure — only the OpenAI Responses API populates it. `RuntimeCompletionOutput.provider_request_id` is therefore usually `None`; do not build features that assume it.
- `Usage` uses `0` as the "not reported" sentinel; `Usage::has_values()` is the only way to distinguish. `usage_from_rig` already encodes this.
- `OneOrMany<T>`'s inherent methods live in `impl<T: Clone> OneOrMany<T>` (`src/one_or_many.rs:27`), there is no `From<Vec<T>>`, and `many()` (`:101`) is fallible with `EmptyListError` (`:25`). Use `OneOrMany::many(vec)?`; `one()` (`:93`) is infallible. `is_empty()` always returns `false` by construction — never branch on it.
- `ProviderRuntimePolicyRecord` is passed into `build_completion_model` but currently ignored (`_policy`). Connect/request timeouts are enforced only by Moira's `tokio::time::timeout` wrappers, not by the Rig client's HTTP layer. Do not claim otherwise in docs.
- `CompletionRequestBuilder::build()` (`src/completion/request.rs:1044`) sets `preamble: None` and `insert(0, Message::system(preamble))` instead. Moira hand-builds `CompletionRequest` in `build_completion_request` and *does* set `preamble`, so the two paths produce different `chat_history`. Never mix them or reason about one from the other.
- The no-status branch of `classify_completion_error` substring-matches `error.to_string()`. It is brittle by acknowledgement; prefer widening `provider_response_status()`-based classification over adding more substrings.
- Rig's `Client` `Debug` redacts `Authorization` and `*api-key*` headers but prints the base URL. That is not sufficient — keep Moira's own hand-written `Debug` impls.

## Validation

```bash
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
```

Tests touching the Rig boundary must prove: the exact credential reaches the provider over real HTTP, no secret or raw provider body appears in any surfaced message, usage zero-sentinels map to absent values, stream item ordering and in-band failures are preserved, and failure classes map to the documented HTTP statuses and codes.
