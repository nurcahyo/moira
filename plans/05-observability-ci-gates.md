# Iteration 05 — Observability & CI/Supply-Chain Gates

Companion to `00-audit-report.md` and `01-roadmap-and-dependencies.md`. MVP gate (P0-4/P1). Depends on iteration 02 (the OpenAPI spec must be honest before this iteration freezes it with a diff gate); depends on iteration 03 for stable middleware error/response shapes that the new snapshot suites assert against. Gates iteration 07 (identity foundation needs a stable, observable, honestly-gated backend to build on).

## Summary

**Objective.** Close three gates that currently read as green but enforce nothing or observe nothing: `cargo deny check` runs in CI with no `deny.toml`, so it either silently no-ops or errors uninformatively; `MOIRA_TELEMETRY__OTEL_ENABLED`/`OTEL_ENDPOINT` are configuration fields with zero code readers (traces are never exported, and the `opentelemetry` crate is a declared-but-unused Cargo dependency); and `src/infra/metrics.rs` exposes only cumulative `AtomicU64` counters (no histograms, no percentiles, no per-route/provider breakdown), while there is no CI gate proving the committed OpenAPI spec matches what the code actually generates, and no systematic suite proving secrets/prompts never leak into HTTP responses, OpenAPI, audit metadata, or logs.

**Why ordered here.** P0-4 (`deny.toml`) is a release-integrity blocker independent of everything else and ships first within this iteration — it's a config file with no code coupling. P1-9 (OTel + histograms) and P1-10 (OpenAPI-diff + leak snapshots) depend on iteration 02 having already made the OpenAPI surface honest (no point locking a spec that still overclaims RAG/memory capability) and iteration 03 having already hardened the error/middleware surface those leak-snapshot suites will assert against. This iteration is the last MVP-gate step on the critical path `02 → 03 → 04 → 05` per the roadmap before a backend-only controlled MVP can be declared shippable.

**User-visible outcome (operator-facing, since this is infra/ops work).** A broken or newly-vulnerable dependency actually fails CI instead of silently passing. An operator who sets `MOIRA_TELEMETRY__OTEL_ENABLED=true` gets real distributed traces in their OTLP collector. `/metrics` exposes latency/TTFT/provider-outcome/DB-pool histograms usable for real SLO dashboards, not just cumulative counters. A future PR that accidentally changes a route without regenerating the OpenAPI spec, or that accidentally logs a secret/prompt, fails CI before merge.

**Included scope.** P0-4 (`deny.toml` + CI enforcement proof), P1-9 (OTel SDK/OTLP wiring behind the existing flags + Prometheus histograms via the **decided** `metrics` + `metrics-exporter-prometheus` stack, replacing the hand-rolled exposition code while keeping every existing series), P1-10 (commit generated OpenAPI spec + CI diff gate; secret-leak and prompt/content-leak snapshot suites).

**Excluded scope.** Grafana dashboard JSON / Alertmanager rules (explicitly P2 per the audit — "Grafana/Alertmanager assets are P2"). SBOM generation, SAST/DAST/secret-scanning-in-CI beyond what's needed to make `cargo deny`/`cargo audit` meaningful (those are P2-10/Phase-6 items, out of scope). Full OTel coverage for SQL/Redis/Rig internals (Phase 6 TODO: "full OpenTelemetry SDK/exporter wiring for HTTP, SQL, Redis, Rig execution, routing, retrieval, embedding, streaming, and workers" — this iteration wires the SDK/exporter and instruments HTTP + execution spans; deep per-subsystem tracing is a documented fast-follow, not blocking). Digest-pinning Docker base images (P2-10).

## Findings Addressed

### P0-4 — Broken/toothless supply-chain CI gate (`cargo deny` has no config)
- `.github/workflows/ci.yml:60-68` (`supply-chain` job) runs `cargo install cargo-audit cargo-deny --locked`, `cargo audit`, `cargo deny check` — but `ls deny.toml` at the repo root returns nothing; confirmed absent anywhere in the repo tree.
- **Impact:** `cargo deny check` with no `deny.toml` either uses `cargo-deny`'s built-in defaults (which are permissive/incomplete and not an intentional policy) or errors out in a way the team has apparently not noticed is uninformative — either way, the team believes license/advisory/ban/source policy is enforced when no *intentional* policy exists. A "green" supply-chain gate that enforces nothing is worse than no gate, because it creates false confidence.
- **Correction:** author a `deny.toml` with `[advisories]`, `[licenses]`, `[bans]`, `[sources]` sections reflecting Moira's actual dependency graph (see Cargo.toml dependency list in Architecture below) and verify the job **fails** on a seeded violation before merging (temporarily add a banned/duplicate/unlicensed crate, confirm red, then remove it).

### P1-9 — OpenTelemetry unwired; Prometheus metrics are aggregate counters only
- `src/config/telemetry.rs:5-25` `init()` only builds a `tracing_subscriber::registry()` with an `EnvFilter` and either JSON or plain `fmt::layer()` — no `opentelemetry`/`opentelemetry_sdk`/`opentelemetry-otlp`/`tracing-opentelemetry` layer is constructed anywhere.
- `src/config/settings.rs:204-213` `TelemetrySettings { service_name, env_filter, json, prometheus_enabled, metrics_path, otel_enabled, otel_endpoint }` — `otel_enabled`/`otel_endpoint` are read nowhere else in the crate (confirmed by grep across `src/`); `grep -rn "opentelemetry" src/` returns **zero** matches even though `opentelemetry = "0.32"` is a direct dependency in `Cargo.toml:19` — the crate is declared but entirely unused, i.e., not partially wired, literally zero lines of code reference it. The SDK/exporter/bridge crates it would need alongside it (`opentelemetry_sdk`, `opentelemetry-otlp`, `tracing-opentelemetry`) are not declared at all.
- `src/infra/metrics.rs:17-28` `MetricsInner` is nine `AtomicU64` fields (`http_requests_total`, four status-class counters, `http_latency_micros_total` as a **cumulative sum**, `public_responses_created_total`, `public_streams_started_total`, `worker_ticks_total`) — no histogram buckets, no percentiles, no labels beyond a single `service` label and a coarse `status_class`, no per-route/per-provider/per-model breakdown, no TTFT metric, no DB-pool-utilization metric, no provider-outcome (success/timeout/circuit-open/etc.) breakdown. `render_prometheus` (`:114-238`) hand-writes Prometheus text format directly (no `prometheus` crate dependency exists either).
- **Impact:** operating even a single-replica controlled MVP with no latency distribution, no TTFT visibility, no trace export — an operator cannot answer "what's my p99?" or "why did this request take 4s?" from `/metrics` or any trace backend today, despite the config surface implying both exist.

### P1-10 — No CI OpenAPI-drift gate; no secret/content-leak snapshot suites
- `.github/workflows/ci.yml` (`rust` job, `:43-58`) runs `cargo fmt --check`, `cargo clippy ...`, `cargo test --workspace --all-features`, and the migration-contract job — no step diffs a committed spec file against `cargo run`-generated (or in-process-generated) OpenAPI JSON.
- `src/http/mod.rs:16-22` builds the `OpenApiRouter` via `utoipa` (`OpenApiRouter::with_openapi(openapi::MoiraApiDoc::openapi())` at `:22`) and exposes it live at `openapi_json`/`docs` routes (`:25-26`, handlers in `src/http/openapi.rs`); `src/http/mod.rs:213` (`#[cfg(test)] mod tests`) has in-process route-coverage assertions, but nothing writes the generated document to a file and nothing in CI compares it against a committed copy — so spec drift (a route added without its DTO documented correctly, a schema change nobody reviewed as an API-surface diff) is invisible in a PR diff.
- Secret-leak assertions today are scattered: `src/security/masking.rs:37-54` unit-tests `mask_plain_secret`/`secret_fingerprint` in isolation; the audit's `setup.rs:165` citation is verified as `src/infra/repositories/setup.rs:165` `readiness_query_never_selects_secret_material` — a unit test asserting `SETUP_READINESS_SQL` never selects columns like `encrypted_payload`/`encrypted_data_key`/`key_hash` (real but narrow: one SQL string, not HTTP/log/audit surfaces). There is **no** systematic suite asserting, over real HTTP response bodies / the generated OpenAPI document / audit-log metadata / structured log output, that no plaintext API key, JWT, decrypted credential, ciphertext, or nonce ever appears — and **no** suite at all for prompt/content leakage (conversation message text, memory content, RAG document text appearing somewhere it shouldn't, e.g. in an audit-log `metadata` blob or an error message).
- `docs/todo.md:112-114` (Cross-Phase Verification): "Add OpenAPI generation validation in CI." / "Add secret-leak snapshot tests for HTTP responses, OpenAPI schemas, audit metadata, and logs." / "Add prompt/content-leak snapshot tests for conversation messages, memories, RAG documents, vector records, retrieval diagnostics, HTTP responses, audit metadata, and logs." — all three match this finding exactly and are still fully open.
- **Impact:** a spec can silently drift from the code that generates it (consumers of the spec — e.g. the future Next.js console in plan 08 — build against a stale contract); a future change could leak a secret or raw prompt/conversation content into a response, log line, or audit record without any test failing.

## Architecture

### Components & ownership (per `docs/project-structure.md`)
- **Config** (`src/config/`): `telemetry.rs` grows from a bare `tracing_subscriber` initializer into the composition root for both the existing `tracing` pipeline *and* the new OTel SDK/exporter — this stays a config-layer concern (initialization only), not a new architectural layer; `settings.rs`'s `TelemetrySettings` fields (`otel_enabled`, `otel_endpoint`) finally get readers, plus additive fields for OTLP protocol/headers/sampling if needed.
- **Infra** (`src/infra/metrics.rs`): gains histogram support. **DECIDED (product owner, 2026-07-25) — adopt the `metrics` facade + `metrics-exporter-prometheus` exporter.** This is no longer an open question; the hand-rolled-buckets alternative is rejected and must not be reopened in implementation. **Rationale:** correct cumulative-bucket semantics, `le="+Inf"` handling, label escaping, and Prometheus exposition formatting come from a well-tested library instead of being re-solved in-tree, and the `metrics` instrumentation macros (`counter!`/`gauge!`/`histogram!`) keep call sites clean. **Accepted cost:** two new direct dependencies, and the existing hand-rolled `render_prometheus` (`src/infra/metrics.rs:114`, with its `write_metric_header` `:241` and `sanitize_label_value` `:257` helpers) is **replaced** by the exporter's own text encoder. Ownership stays in `src/infra/metrics.rs`; callers (HTTP middleware, `execution.rs`, DB pool) call recording methods on `MetricsRegistry`, unchanged from today's pattern (`record_http_response`, `record_public_response_created`, etc.) — the facade lives **behind** `MetricsRegistry`, and no `metrics::*` macro is called from outside `src/infra/metrics.rs`.
- **HTTP** (`src/http/`): tracing spans for OTel gain HTTP-layer instrumentation (method/route/status as span attributes, matching the `tower-http` `trace` feature already declared in `Cargo.toml:32` `tower-http = { version = "0.6", features = ["cors", "request-id", "trace", "util"] }`; `TraceLayer::new_for_http()` is applied in `build_router` at `src/lib.rs:43`, so the `tracing-opentelemetry` bridge layer picks up its request spans without touching the existing `TraceLayer` usage).
- **Application** (`src/application/execution.rs`, `src/application/public.rs`): gain explicit metric recording calls at phase boundaries (attempt start/end, TTFT for streams, provider outcome classification) — additive calls only, no control-flow change.
- **CI** (`.github/workflows/ci.yml`): `supply-chain` job gains meaning via `deny.toml`; `rust` job gains an OpenAPI-diff step and the new snapshot-suite test targets (they run as part of `cargo test --workspace --all-features` if implemented as `#[test]`s, or as an explicit new step if implemented as a separate binary/script — prefer `#[test]`s for consistency with the existing test suite and CI simplicity).
- **New root file**: `deny.toml` (P0-4). **New/generated file**: a committed OpenAPI spec artifact, e.g. `docs/openapi.json` (P1-10) — exact path is a naming decision, see Detailed Implementation.

### Data flow
- **Supply-chain**: `cargo deny check` reads `deny.toml` + `Cargo.lock` at CI time, cross-references `[advisories].db-urls`/RustSec advisory DB, `[licenses].allow` list, `[bans]` duplicate/banned-crate rules, `[sources]` allowed-registry list — fails the job (non-zero exit) on any violation, which fails the `supply-chain` GitHub Actions job, which (assuming branch protection requires it — verify/flag) blocks merge.
- **OTel**: `telemetry::init()` is called once from `main.rs:22` before `Settings::validate` consumers spin up the server; when `settings.telemetry.otel_enabled`, it additionally constructs an OTLP exporter (gRPC or HTTP, pick one — see Decisions below) pointed at `settings.telemetry.otel_endpoint`, wraps it in a `BatchSpanProcessor`, builds a `tracing_opentelemetry::layer()` bridging the existing `tracing` spans into OTel spans, and adds that layer to the same `tracing_subscriber::registry()` alongside the existing `fmt::layer()` — so existing `tracing::info!`/`#[instrument]` call sites (if any exist — verify current `#[instrument]` usage density, since if none exist, span quality will be poor until instrumentation is added at key boundaries: HTTP request span, execution attempt span, provider-call span) automatically flow to both destinations. On graceful shutdown (`main.rs:72-79`, after `axum::serve` returns and before `worker_supervisor.shutdown()`), flush the OTel exporter (`TracerProvider::shutdown()` / equivalent) so in-flight spans aren't dropped.
- **Metrics**: HTTP middleware (`record_http_response` is called from the middleware in `src/lib.rs:88`) additionally records latency into a histogram keyed by a **low-cardinality** route label (not raw path with IDs — reuse whatever route-templating mechanism, if any, `tower-http`'s `TraceLayer` already provides, or derive one; the existing `sanitize_label_value`/low-cardinality-label pattern at `src/infra/metrics.rs:257-267` and the existing test asserting `!rendered.contains("path=")` at `:284` signal the team already deliberately avoids high-cardinality path labels — preserve that discipline, use route templates like `/api/v1/admin/applications/{id}`, not the raw resolved path). `execution.rs` records execution-latency and TTFT (time from stream start to first delta — `execute_rig_stream`/`supervise_public_stream` already have the relevant timestamps in scope) and provider-outcome counts (success/timeout/circuit-open/fallback) per provider+model label pair (bounded cardinality — provider/model counts are small and admin-controlled, unlike arbitrary user input). DB pool utilization is read from `sqlx::PgPool`'s own introspection (`pool.size()`, `pool.num_idle()` — confirm exact `sqlx` 0.8 API) sampled on each `/metrics` scrape or on an interval, not per-request.
- **OpenAPI diff gate**: a new CI step runs the binary (or a dedicated `#[test]`) that calls `openapi::MoiraApiDoc::openapi()` (the same in-process generation `src/http/mod.rs:22` already uses to build the live router), serializes it to JSON, and `diff`s it byte-for-byte (or structurally, to avoid key-ordering false positives — prefer serializing through `serde_json::to_string_pretty` with a stable key order, or comparing parsed `serde_json::Value` equality rather than raw text) against the committed `docs/openapi.json`. Mismatch fails CI with a clear message ("OpenAPI spec is stale — run `cargo run --bin generate-openapi > docs/openapi.json` and commit").
- **Leak snapshot suites**: new integration tests that (a) drive representative HTTP requests/responses through the real router (reusing `tests/support/mod.rs` harness patterns already used throughout the test suite) and assert response bodies never contain configured secret markers (raw API keys, decrypted credential values, JWT signatures, AES-GCM ciphertext/nonce bytes) via substring/regex denylist checks against known test-fixture secret values; (b) serialize the generated OpenAPI document and assert no `example`/`default` value anywhere contains a real-looking secret pattern; (c) query `audit_logs.metadata` after test flows and assert no secret/prompt substrings; (d) capture `tracing` output (via a test-local subscriber/writer, e.g. `tracing_subscriber::fmt::TestWriter` or a custom `Layer` collecting events into a buffer) during representative flows and assert the same denylist.

### Security boundaries
No new trust boundary crossed by observability wiring — OTLP export sends **span metadata** (route templates, status codes, durations, provider/model identifiers) to a configured collector, never request/response bodies, never credentials, never prompts; this must be enforced by construction (span attributes are explicitly whitelisted fields, not `Debug`-dumped structs) and verified by the new leak-snapshot suites extended to also cover captured span attributes if OTel is enabled during a test run (nice-to-have; the log/HTTP/audit/OpenAPI coverage is the hard requirement). `deny.toml`'s `[advisories]` section is itself a security control (supply-chain vulnerability gate) — treat its authoring as security-sensitive, not routine config.

### DB/migration changes
None. This iteration touches no schema.

### Backward compatibility
- `deny.toml` addition is invisible to API consumers (CI-only).
- OTel wiring is opt-in via existing `otel_enabled` flag, defaulting `false` (`settings.rs:678`) — zero behavior change for operators who don't set it.
- New histogram metrics are additive to `/metrics` output — any existing scraper continues working, gains new series.
- OpenAPI diff gate is CI-only, no runtime behavior change; if it reveals current drift on day one, resolving that drift is in scope for this iteration (see Definition of Done).

### Deployment implications
- The decided histogram stack (`metrics` + `metrics-exporter-prometheus`) adds a new transitive dependency tree — re-run `cargo deny check` against it as part of authoring `deny.toml` so the two P0-4/P1-9 work streams don't conflict (sequencing note in Multi-Agent Workflow). Both crates are MIT-licensed; confirm their transitive set (notably `metrics-util`, `quanta`, `mach2`/`libc`, `indexmap`, `hashbrown`) against `[licenses].allow` rather than assuming.
- `metrics-exporter-prometheus` must be declared with `default-features = false`. Its default features start an **independent HTTP listener** (and optional push-gateway client); enabling them would expose a second, unauthenticated metrics surface that bypasses `settings.telemetry.prometheus_enabled` entirely. Moira serves `/metrics` itself through Axum and only needs the recorder plus `PrometheusHandle::render()`. Treat this as a security requirement, not a build-size preference.
- OTel OTLP exporter requires network egress from the Moira pod to the configured collector endpoint when enabled — Helm chart `NetworkPolicy` (`charts/moira/templates/networkpolicy.yaml`, flagged in audit P2-11 as currently broad `0.0.0.0/0` egress) already permits arbitrary egress today, so no chart change is strictly required for this iteration to function, but document the new egress dependency in deployment docs; tightening the network policy to specifically allow the OTel collector is P2-11's job, not this iteration's.
- No new secret required unless the OTLP endpoint needs auth headers (some collectors do) — if so, add an additive `TelemetrySettings.otel_headers: Option<HashMap<String,String>>` field (or reuse a generic auth-header config pattern already present elsewhere in the codebase — check `src/config/settings.rs` for a precedent before inventing a new shape).

### Failure & recovery
- If the OTLP endpoint is unreachable, the exporter must **not** block or fail request handling — `BatchSpanProcessor` already buffers/drops asynchronously by design; verify the configured export timeout is short and that a collector outage degrades to "traces silently dropped" not "requests slow down," and add a startup/periodic warning log (not a panic) when export failures are observed repeatedly.
- `cargo deny check` failing in CI is the intended "recovery" mechanism — a real advisory/license/ban violation blocks merge until resolved (upgrade, allow-list with justification, or remove the dependency).
- OpenAPI diff-gate failure is resolved by regenerating and committing the spec — document the exact regeneration command in the CI failure message and in this plan.

### Module 3 — Prometheus histograms (P1-9b)

**DECIDED — adopt the `metrics` facade + `metrics-exporter-prometheus` exporter.** The hand-rolled-buckets option is rejected. Implement to this decision; do not re-litigate it in the PR.

**Rationale (record verbatim in the PR):** correct cumulative-bucket semantics (every observation increments all buckets at or above its value), `le="+Inf"` bucket handling, Prometheus label escaping, and `_bucket`/`_sum`/`_count` exposition formatting come from a well-tested library rather than being re-solved in-tree, where each is an easy and silent bug; the `metrics` instrumentation macros keep call sites clean.

**Accepted cost (record verbatim in the PR):** two new direct dependencies, and the existing hand-rolled `render_prometheus` (`src/infra/metrics.rs:114`) plus its `write_metric_header` (`:241`) and `sanitize_label_value` (`:257`) helpers are **deleted and replaced** by the exporter's encoder.

#### 3.1 Exact `Cargo.toml` additions

Append to the existing `[dependencies]` table (`Cargo.toml:7-…`), next to the other infra crates:


#### 3.2 Recorder ownership: per-registry, never a process-global install

**Do not call `PrometheusBuilder::install()` / `metrics::set_global_recorder`.** Moira's integration suite constructs multiple `AppState`s in a single test process (`tests/support/mod.rs`), and a process-global recorder would merge series across unrelated app instances and would panic on the second install. Instead:

- `MetricsRegistry` owns a `PrometheusRecorder` built with `PrometheusBuilder::new() … .build_recorder()` and the `PrometheusHandle` obtained from it, both behind the existing `Arc<MetricsInner>` so `MetricsRegistry` stays `Clone` + `Send` + `Sync` exactly as today.
- Every `record_*` method wraps its macro calls in `metrics::with_local_recorder(&self.inner.recorder, || { … })`. The wrapping is entirely inside `src/infra/metrics.rs` and each closure is synchronous, so the thread-local the helper installs is always live for the recording call — no call site outside this module ever touches a `metrics::*` macro.
- `render_prometheus` calls `self.inner.handle.render()`.
- The `service` label that every family carries today becomes a builder-time global label: `PrometheusBuilder::new().add_global_label("service", service_name)`. That requires the service name at construction, so `MetricsRegistry::new()` gains a `service_name: &str` parameter. Its one production call site is `src/app/state.rs:64`, where `settings` is already in scope — a one-line change to `MetricsRegistry::new(&settings.telemetry.service_name)`.
- `render_prometheus`'s existing signature `(&self, service_name, redis_enabled, workers_enabled) -> String` is **kept**, with the first parameter renamed to `_service_name` (now redundant, since the label is applied at build time; leaving it un-underscored would trip `unused_variables` under `-D warnings`). This keeps `src/http/observability.rs` **byte-untouched**, which is the mechanical guarantee that the endpoint's gating, `404`/`metrics_disabled` error contract, content-type, cache-control, and unauthenticated posture survive the exporter swap unchanged.
- Bucket boundaries are configured once on the builder via `.set_buckets_for_metric(Matcher::Full("moira_http_request_duration_seconds"), &[…])` (and equivalents for the execution-latency and TTFT families) rather than being hardcoded at each call site. Use second-denominated boundaries (Prometheus convention) even though the legacy counter is in microseconds.

#### 3.3 Migration path for the existing `AtomicU64` counters (`src/infra/metrics.rs:17-28`)

**DECIDED: replace, do not keep-and-bridge.** Every field of `MetricsInner` (`:17-28`) stops being an `AtomicU64` and becomes a `metrics::counter!` emission through the local recorder. **Justification:** keeping the atomics *and* emitting through the facade means two independent sources of truth for the same series, which can and eventually will diverge (one call site updated, the other forgotten) — precisely the class of bug adopting a library is meant to eliminate. There is also nothing to bridge *to*: the atomics have no consumer outside this module.

Concretely:

- **Method surface is unchanged**, so no call site outside `src/infra/metrics.rs` changes: `record_http_response` (`:47`), `record_public_response_created` (`:76`), `record_public_stream_started` (`:82`), `record_worker_tick` (`:88`) keep their signatures. Verified call sites that must compile untouched: `src/http/public.rs:75,129,406,420`, `src/infra/workers.rs:149`, and `metrics_middleware` in `src/lib.rs:80-90`.
- **Emitted metric family names are unchanged**, so no existing scraper breaks: `moira_http_requests_total`, `moira_http_responses_{2xx,3xx,4xx,5xx}_total`, `moira_http_latency_micros_total`, `moira_public_responses_created_total`, `moira_public_streams_started_total`, `moira_worker_ticks_total`, plus the `redis_enabled`/`workers_enabled` feature gauges. Snapshot the current `/metrics` body before the change and diff it against the post-change body; only **additions** are permitted.
- **`MetricsSnapshot` (`:30-40`) and `snapshot()` (`:94`) are removed.** They are `pub` but have exactly two callers — `render_prometheus` itself (`:120`) and the module's own unit test (`:278-280`) — and neither survives: the exporter renders from its handle, not from a struct. Removing them is an internal-crate API change only; it touches no HTTP surface and no OpenAPI schema. If a future consumer needs programmatic read-back, it parses `render_prometheus()`'s output — one source of truth.
- **`http_latency_micros_total` is KEPT, not deprecated or removed** (this resolves the keep/deprecate question the plan raises at Module 3's bullet list, the PR description requirements, and Risks & Rollback). It is re-emitted as a plain `metrics::counter!("moira_http_latency_micros_total")` incremented by the same `latency.as_micros()` value in `record_http_response`, **alongside** the new `moira_http_request_duration_seconds` histogram. **Justification:** removing it is a breaking change for any scraper computing average latency from the cumulative sum, and this iteration's whole premise is that it freezes the surface rather than changing it — the PR's "Breaking API/OpenAPI changes" section must be able to say *none*. Keeping it costs one counter increment per request. Mark it in its `# HELP` text as superseded by the histogram (`describe_counter!`), and record the removal as a **deferred follow-up** for a later plan that can carry a breaking `/metrics` change deliberately.
- **The low-cardinality discipline survives the deletion of `sanitize_label_value`.** The exporter escapes label *values* correctly for the text format, but escaping is not the same guarantee as *cardinality*: it will happily render a UUID. The existing test at `:284` (`assert!(!rendered.contains("path="))`) and its new-family successors (Verification) are what enforce this, plus the rule that route labels come from `axum::extract::MatchedPath`, never the raw URI.

## Risks & Rollback

**Security**: `deny.toml` authored too loosely reproduces P0-4's original problem (a green gate that doesn't actually enforce policy) — mitigated by the mandatory seeded-violation verification step in the Definition of Done. OTel span attributes must be whitelisted fields only, never raw request/response bodies or secret material — mitigated by the leak-snapshot suite extension noted in the Security boundaries section (nice-to-have coverage) and by manual review of every new span/attribute call site (mandatory read-only-reviewer checklist item).

**Data-migration**: none — no schema changes this iteration.

**Compatibility**: the `/metrics` output changes (new metric families), but the change is **additive only** — the decision in Module 3 §3.3 keeps `http_latency_micros_total` and every other pre-existing family name and its `service` label, so no external scraper or dashboard breaks. The real compatibility risk moves from "did we remove a series?" to "did the exporter render a series differently than the hand-rolled code did?" — mitigated by the mandatory before/after `/metrics` body diff in the PR and by `metrics_endpoint_still_exposes_every_pre_existing_metric_family`. Deleting `http_latency_micros_total` is deferred to a later plan that can carry a deliberate breaking `/metrics` change, in the manner of plan 04's P1-8 `If-Match` change.

**New-dependency risk (histograms)**: `metrics` + `metrics-exporter-prometheus` are now load-bearing for an operator-facing endpoint. A future major bump of either could change exposition details; the unit tests named in Verification are deliberately written as characterization tests over the encoder output so such a bump fails loudly rather than silently altering `/metrics`. If the pair ever becomes unmaintained, the rollback is bounded: `MetricsRegistry`'s method surface is unchanged by this plan, so a replacement encoder is a single-module swap behind it.

**Deployment**: enabling OTel requires network egress to a collector — currently unrestricted by the Helm chart's network policy (P2-11, unchanged by this iteration) so no chart change is required to function, but operators enabling it in a hardened environment need to know to open egress; document this. New dependencies (OTel SDK crates, possibly a histogram crate) increase binary size and build time modestly — not expected to be a deployment blocker but worth noting in the PR.

**Rollback procedure**: `deny.toml` can be reverted (delete the file) instantly if it's found to incorrectly block a legitimate dependency in an emergency, restoring the pre-iteration (toothless but non-blocking) state — though this reintroduces P0-4, so treat as a last resort, not a routine lever; prefer fixing the policy file. OTel wiring is fully gated behind `otel_enabled` — disabling it via config (no code rollback needed) instantly reverts to pre-iteration tracing-only behavior. The OpenAPI diff gate and leak-snapshot suites are CI-only additions with no runtime code path — reverting them (removing the CI step / skipping the test) has zero production impact, only reduces future-regression protection.

**Deferred follow-ups**: Grafana dashboard JSON + Alertmanager rules (P2, explicitly out of scope); full OTel coverage for SQL/Redis/Rig-internal spans (Phase 6 TODO, this iteration covers HTTP + execution-attempt spans only); digest-pinning Docker base images and SBOM generation (P2-10, unrelated to this iteration's scope but adjacent — flag for plan 06 or a dedicated hardening pass); tightening `charts/moira` network policy to specifically scope OTel collector egress instead of broad `0.0.0.0/0` (P2-11); removing the superseded `moira_http_latency_micros_total` counter once dashboards have migrated to `moira_http_request_duration_seconds` (a breaking `/metrics` change, deliberately not taken here).
